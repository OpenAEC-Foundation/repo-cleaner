# Code Convention Scanner Design

## Goal

Extend `repo-cleaner` so it can scan repositories for naming convention violations, automatically propose safe fixes, and keep a single scanner-managed pull request up to date per repository.

The scanner must work in GitHub Actions without requiring repository-specific setup from the user. Any tool configuration generated by the scanner must be temporary and must never be committed into the pull request.

## Scope

The first version covers:

- Repository name validation and optional rename
- Directory naming validation and autofix
- Source file naming validation and autofix
- PHP naming validation and autofix
- C++ naming validation and autofix
- JavaScript naming validation and autofix
- Source files larger than `1000` lines, reported as violations

The first version must support repositories that contain any mix of the supported languages.

Repository discovery excludes hidden metadata, dependency-owned trees such as `node_modules`, `vendor`, and `third_party`, and generated `dist` trees. Organization naming rules apply only to repository-owned source. Source files containing lines longer than 4096 bytes are treated as generated or minified: path and size checks still apply, but document-symbol analysis is skipped to bound language-server responses.

## Non-Goals

- Requiring maintainers to add or keep convention config files in their repositories
- Building a regex-only renaming engine for code identifiers
- Exiting on the first failure or first violation
- Creating a new pull request on every scan run

## Design Summary

The system is implemented in DynLex. `repo_conventions_enforcer.dl` is a thin executable entrypoint, while parsing, scanning, language-server integration, GitHub operations, and reporting live in focused DynLex modules.

The scanner operates on a live temporary clone. It does not calculate a full fix plan up front. Each phase mutates the current repository state, refreshes its view, and continues from the updated structure. This is required because renames change later paths, imports, and symbol references.

Where a language-specific tool can safely own a convention phase, the scanner uses that tool instead of custom text replacement. DynLex remains responsible for orchestration, execution order, temporary workspace management, and final reporting.

Across rename phases, the scanner must select one authoritative refactoring backend per rename category and language combination before mutation begins. Once selected, that backend is the only rename mechanism for that phase.

## Architecture

### Module Layout

- `repo_conventions_enforcer.dl`
  - Converts host command-line arguments and dispatches the program
- `src/cli.dl`, `src/program.dl`, `src/manager.dl`
  - Parse flags, load inputs, process one or many repositories, print summaries, and select the exit code
- `src/github.dl`
  - Owns all GitHub and git operations, including issues, pull requests, file updates, clones, branches, commits, and pushes
- `src/convention_source.dl`, `src/conventions.dl`
  - Cache, validate, and expose convention patterns and name conversions
- `src/scanner.dl`
  - Discovers live repository structure, detects supported languages, selects path renames, and checks the `>1000` line rule
- `src/language_server.dl`, `src/language_server_paths.dl`
  - Provide shared LSP-backed symbol, path, and reference updates for PHP, C++, and JavaScript
- `src/enforcer.dl`, `src/application.dl`
  - Execute ordered live mutations, manage temporary clones, format C++ sources, and publish scanner changes
- `src/repository_checks.dl`, `src/reporting.dl`
  - Handle repository-level policies, issue lifecycle, and human-readable reports

### Package Rules

- Protocol behavior is shared across language backends; only backend commands and initialization options vary
- GitHub and git logic is not duplicated across modules; `src/github.dl` owns both local and remote operations
- The CLI module does not contain GitHub logic, file traversal logic, or language-specific rewrite logic

## Execution Model

The scanner must work against the current repository state at every phase.

- It must not precompute a global list of fixes and apply them later
- It must apply one rename at a time where path mutations are involved
- It must refresh file discovery and reference targets after each mutation
- It must report violations against the final live path or identifier after previous renames have been applied

This is especially important for directory renames, because later file paths and code references depend on earlier directory changes.

## Backend Selection Policy

The scanner must not combine multiple rename strategies for the same rename phase.

- Select one authoritative backend for each rename category and language combination during preflight
- If a language server or equivalent refactoring backend supports the rename category, use that backend directly
- Do not attempt a fallback rename strategy when the selected backend fails
- Do not retry the same rename through a second mechanism after a failed attempt
- If the selected backend returns a structured refusal before mutation, leave that violation report-only, record the reason, exclude that exact candidate for the current operation, and continue with later candidates without retrying it
- If the backend transport fails, returns malformed data, or fails after any mutation, stop further mutation for that repository and mark the repository scan as failed

This avoids conflicting rewrites and prevents partial “best effort” renames from masking tool failures.

## Conventions And Rule Coverage

### Directly Supported In V1

- Repository names
- Directory names
- Source file names
- Class-like symbols
- Function-like symbols
- Variable-like symbols
- Source files over `1000` lines

### Schema-Driven Optional Categories

The scanner should be written so these can be added cleanly if the conventions schema defines them:

- Namespace or module names
- Constant-like symbols
- Enum-like symbols

If the conventions schema does not define a category, the scanner must skip that phase cleanly instead of inventing a rule.

Case conversion preserves the complete ordered word sequence. It must not replace long names with initials, because casing rules do not authorize lossy abbreviation and unrelated names can collapse to the same identifier. Only explicit identifier spellings are symbol candidates; language-server labels for anonymous callbacks and other synthesized document symbols are ignored.

## Supported Languages

### PHP

- Scan only when PHP source files are present
- Prefer AST-aware tools or libraries for renaming
- Do not rely on raw search-and-replace for identifier updates

### C++

- Scan only when C++ source files are present
- Use clangd symbol and workspace edits for naming enforcement
- Apply C++ symbol edits only when a root `compile_commands.json` gives clangd project-wide index input; otherwise report that symbol mutation was not attempted
- Use temporary configuration files generated by the scanner if needed
- Use `clang-format` after renames across the full repository set of supported files

### JavaScript

- Scan only when JavaScript source files are present
- Use TypeScript language-server symbol and workspace edits for renames
- Apply JavaScript symbol edits only when a root `jsconfig.json` or `tsconfig.json` gives the TypeScript language server project-wide index input; otherwise report that symbol mutation was not attempted
- Do not rely on raw text replacement for identifier updates

## Temporary Configuration Policy

The scanner may generate temporary files inside the temporary clone to drive external tools. Examples include:

- `.clang-tidy`
- `compile_commands.json`
- temporary formatter configs
- temporary codemod manifests

Rules:

- Generated config must be ephemeral
- Generated config must never be staged or committed
- Generated config must be removed before commit creation
- Repositories must not be required to keep any config produced by the scanner

## Reference Update Policy

Directory, file, and symbol renames must update safe references in code before the next rename phase continues.

For all rename phases, the scanner must use the single selected authoritative rename backend for that phase. If a language server or equivalent language-aware refactoring backend is selected, it must perform both the rename and the related reference updates. The scanner must not fall back to narrower rewriting when that backend fails.

Reference update coverage includes, when safely rewritable:

- include paths
- import paths
- require paths
- relative source references

Reference updates are part of rename execution, not a separate reporting-only phase.
Before a path mutation, the scanner must also prove that Git does not ignore the destination spelling. An ignored destination is report-only because ordinary publication would stage the tracked source deletion without its ignored replacement.

File naming rules apply to the first filename segment. Dot-separated suffixes are explicit ecosystem literals and remain byte-identical, so `BadBrowser.test.js` becomes `bad_browser.test.js` while `vite.config.js` remains unchanged.

Language-server preparation does not prove arbitrary manifest, workflow, documentation, or source-string references. Before applying a prepared path rename, the scanner must find occurrences of the source filename in every tracked or non-ignored untracked file. Every occurrence outside the renamed path must be in a document changed by the authoritative language-server workspace edit. Otherwise the rename is report-only and the unresolved file is named in the report.

## Order Of Operations

The scanner must execute phases in this order:

### Preflight

1. Load conventions
2. Detect external tools available in the current environment
3. Select one authoritative rename backend per rename category and language combination
4. Verify GitHub authentication and required repository permissions

### Mutation And Validation

1. Rename the repository if required
2. Clone the repository
3. Rename directories one by one
   - Process the current live tree
   - Refresh structure after each rename
   - Use the selected authoritative rename backend and its reference update capability
   - If the backend fails, stop further mutation for that repository and mark the repository scan as failed
4. Detect which supported languages are present in the cloned repository
   - A single repository may contain any mix of PHP, C++, and JavaScript
5. Rename files one by one
   - Use the selected authoritative rename backend and its reference update capability
   - If the backend fails, stop further mutation for that repository and mark the repository scan as failed
6. Rename namespace or module-like symbols if the conventions schema defines them and the selected backend can do this safely
   - Use the selected authoritative rename backend
   - If the backend fails, stop further mutation for that repository and mark the repository scan as failed
7. Rename class or type-like symbols
   - Use the selected authoritative rename backend
   - If the backend fails, stop further mutation for that repository and mark the repository scan as failed
8. Rename function or method-like symbols
   - Use the selected authoritative rename backend
   - If the backend fails, stop further mutation for that repository and mark the repository scan as failed
9. Rename variable-like symbols
   - Use the selected authoritative rename backend
   - If the backend fails, stop further mutation for that repository and mark the repository scan as failed
10. Rename constant or enum-like symbols if the conventions schema defines them and the selected backend can do this safely
   - Use the selected authoritative rename backend
   - If the backend fails, stop further mutation for that repository and mark the repository scan as failed
11. Run `clang-format` across the full repository set of supported files
12. Re-scan the final tree
   - Report remaining naming violations against final names and final paths
   - Report source files over `1000` lines here as part of the final state
13. Commit changes
14. Push the scanner branch
15. Create or update the scanner pull request
16. Exit non-zero if violations were found or any phase failed

## Pull Request Lifecycle

The scanner must prevent pull requests from stacking up.

### Ownership Rule

Ownership is determined by a single canonical branch name:

- `repo-cleaner/convention-fixes`

The branch name alone is the ownership signal. The scanner does not need a label for pull request ownership.

### Behavior

- Before creating a PR, look for an open PR whose head branch matches the canonical scanner branch
- If one exists:
  - reuse that branch
  - push updated fixes to it
  - update the existing PR title and body
- If one does not exist and there are changes:
  - create a new PR from the canonical branch
- If no changes remain and a scanner PR is open:
  - close the PR as resolved

### Anti-Stacking Rules

- Never create a unique branch name per run
- Never create a second PR when the canonical scanner branch already has one
- Prefer replacing the branch contents with the current full fix set

## Failure And Exit Behavior

The scanner must finish its work before failing the job.

- It must continue through all phases and supported languages even when violations are found
- If a selected rename backend fails, it must stop further mutation for that repository immediately
- It must continue through other repositories when one repository has scan failures, if the command targets multiple repositories
- It may record phase failures and include them in the terminal summary and PR body
- The final process exit code must be non-zero when:
  - violations were found
  - fixes were proposed
  - any phase failed
- The final process exit code may be zero only when:
  - no violations remain
  - no fixes were needed
  - no scan phase failed

This keeps GitHub Actions red while still allowing the scanner to finish, push changes, and update or create the PR.

## Workflow Requirements

The reusable GitHub Actions workflow must install all required dependencies itself.

The user should not have to:

- add local tool config files
- pre-clone repositories
- manually prepare temporary workspaces
- maintain per-repository scanner settings just to make the scanner run

## Reporting Requirements

The terminal summary and PR body must describe:

- which phases ran
- which languages were detected
- which violations were fixed
- which violations remain
- whether the repository now has an open scanner-managed PR
- whether any source files exceed `1000` lines
- whether any backend or tool phase failed

The final report must reflect the repository's final state after all attempted fixes.

## Safety Requirements

- Do not commit temporary configuration files
- Do not rewrite identifiers with naive text replacement when a safer language-aware backend is available
- Do not switch to a second rename mechanism after a selected rename backend fails
- Do not update arbitrary human-owned pull requests
- Do not create multiple scanner pull requests for the same repository
- Do not stop after the first violation

## Implementation Direction

The implementation approach is:

- DynLex orchestration for workflow, ordering, GitHub integration, reporting, caching, and temporary workspace management
- LSP backends for language-specific identifier and reference rewrites
- Incremental, live-tree mutation instead of batch fix planning

This keeps the system consistent with the current repository while making the scanner capable of handling real code naming updates across multiple languages.
